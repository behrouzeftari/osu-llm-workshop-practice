Lesson 3: Special Permissions & Practice

Beyond the basic rwx bits, Linux has three special permission bits that change how programs run or how directories behave.

The three special bits

NameSymbolOctalOn a fileOn a directory
Setuids in owner execute4000Run with owner's privileges— (ignored)
Setgids in group execute2000Run with group's privilegesNew files inherit directory's group
Sticky bitt in others execute1000— (obsolete)Only owner can delete/rename files inside

Setuid — run as the file's owner

When a file has setuid and is executed, the process runs with the file owner's UID, not the runner's. Classic example: /usr/bin/passwd (owned by root) lets users change their own password by briefly running as root.

$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 68208 Jan 12  2024 /usr/bin/passwd
            ^--- 's' means setuid + execute

Security note

Setuid programs are a favorite attack target. Only use when necessary. Prefer sudo or capabilities for custom tools. Many distros now use capabilities instead of setuid for things like ping.

Setgid on directories — shared group workspace

When a directory has setgid, new files created inside inherit the directory's group, not the creator's primary group. This is the standard way to make a shared folder for a team.

# Set up a shared project folder
mkdir /projects/web
chgrp developers /projects/web
chmod 2775 /projects/web   # 2 = setgid, 775 = rwxrwxr-x

$ ls -ld /projects/web
drwxrwsr-x 2 root developers 4096 Nov  9 11:00 /projects/web
            ^--- 's' in group position = setgid + execute

Now any developer in the developers group can create files, and those files will automatically belong to the developers group.

Sticky bit — /tmp protection

On a world-writable directory like /tmp, the sticky bit prevents users from deleting or renaming each other's files. They can only remove their own.

$ ls -ld /tmp
drwxrwxrwt 14 root root 4096 Nov  9 11:30 /tmp
               ^--- 't' = sticky + execute for others

Setting special bits with chmod

chmod u+s program         # Setuid
chmod g+s directory       # Setgid on directory
chmod +t directory        # Sticky bit
chmod 4755 program        # Numeric: 4=setuid, 2=setgid, 1=sticky
chmod 2775 shared/        # Setgid + rwxrwxr-x
chmod 1777 temp/          # Sticky + rwxrwxrwx

Capital S / T

If you see S or T (capital), the special bit is set but the corresponding execute bit is not. Example: chmod u+s file on a file without owner execute → shows S. This is usually a mistake — fix with chmod u+x.

Hands-on scenario: The course dropbox

Scenario

You're a TA for a course. Students need to submit assignments to a shared folder. Requirements:

  1. Students can create files in the folder.
  2. Students cannot read, modify, or delete each other's submissions.
  3. TAs (group tas) can read all submissions.
  4. The instructor (user prof) owns the folder and has full access.

Solution

# Create and set ownership
mkdir /course/dropbox
chown prof:tas /course/dropbox

# Permissions:
# prof (owner): rwx
# tas (group):  r-x  (read/traverse, no write)
# students (others): -wx (create/traverse, NO read, NO delete others)
# sticky bit: prevent students deleting each other's files
chmod 1753 /course/dropbox

# Verify
$ ls -ld /course/dropbox
drwxr-x-wt 2 prof tas 4096 Nov  9 12:00 /course/dropbox

Why this works:

  • owner = rwx (7): prof has full access.
  • group = r-x (5): tas can list (r) and enter (x) the directory to read submissions.
  • others = -wx (3): students can enter directory (x) and create files (w), but cannot list contents (no r). Note: on Linux, ls without read permission still shows filenames if you have execute — this is kernel behavior; true secrecy needs other tools.
  • Sticky bit (t, the leading 1): students can't delete/rename files they don't own.

Verified behavior

Tested in a disposable directory: chmod 1753 produces drwxr-x-wt (group gets r-x). The original 1733 gave group -wx (3), not r-x (5). Also, chmod -R 644 breaks directory traversal — use chmod -R a+rX instead.

In the shared project folder example, what problem does the setgid bit on the directory solve? What would happen to new files' group ownership without it?

In the dropbox scenario, why does "others" need execute (x) but not read (r) on the directory? What would break if you removed execute? What would break if you added read?
